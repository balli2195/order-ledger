How the Lead DB works

The Lead DB is the list of store products we have matched to an Amazon ASIN, plus everything we learn about them over time: store prices, Amazon prices, competitors' offers and stock, and your decisions. It feeds the daily buy queue today. It is also being built up as training data for the next Lead Score model. Written Nov 11, 2026; the numbers below are live.

Built for a much bigger table

  • One table for every store. Each catalog and candidate row carries a store column. A second store adds rows, not tables. The page shows a store filter as soon as there are 2 stores.
  • Indexes on what the page and jobs ask for: store + brand, ASIN, unchecked matches, and candidates by store and status. A page of the catalog reads one index range, not the whole table, so it stays fast at 100,000+ rows.
  • The biggest data lives apart from the catalog. Keepa products (about 0.3 MB each compressed) sit in keepa_raw, stored as-is without recompression. Snapshots are split by month, so old months can be moved out to files without touching recent ones.
  • Same database as orders and leads. Joins between your leads, the catalog and Keepa data are one query, with no copying between systems.

Using the Lead DB page

  • To review: today's candidates. Approve creates a lead on the Leads tab. Reject asks for a reason (ROI too low, historical price too low, too many sellers, can't sell / gated, not in stock, or your own words). Reasons are kept with the candidate and used in training (below).
  • Decided: what was approved or rejected, and by whom.
  • Catalog: every matched pair, filterable by store and brand. OK confirms a match (the jobs then never doubt it). Wrong match asks why. Multi-size items take a size answer.
  • Archived lists: one-off re-priced lists (spring 2026 Sephora sale, Chanel). Each row shows whether the ASIN is already a lead in the current sale, and can be marked wrong.

How it learns from wrong matches

  1. You mark a pair wrong and tick why: size, shade, concentration (EDT vs EDP), set, bonus item, multi-pack, version, product, or other, with an optional note and the correct ASIN.
  2. The first six reasons are automatic checks. One mark turns that check on for that brand. When the same reason shows up in 3 or more brands, it turns on for every brand.
  3. Every run then applies them: new matches that break a check are kept at low confidence (never proposed), the weekly run downgrades existing unconfirmed pairs that break one, and the daily run holds them back. A pair you marked OK is never held back.
  4. Version, product and other have no automatic check. The weekly run lists their notes for Claude, which adds a word rule (for example "block tester in Amazon titles for Chanel") only when several marks show the same pattern, and tells you in the weekly message.
  5. For training, every pair marked wrong is dropped, so a bad match can't teach the model a fake price.

Training: how the Lead DB feeds Lead Score

Today: Lead Score v1 built

v1 predicts the ROI you'd get selling at the average Buy Box price on days 18–78 after the lead date (lowest FBA price on days with no Buy Box). It learned from 12.5k of your past leads (Apr 2024 – Aug 2026). Its inputs are price history (32% of its weight), competitor offers and stock (29%), brand track record (17%) and smaller families. Its weakest input is competitor stock: Keepa only returns the offers and stock as of the day we pull, so for older leads the model sees today's competitors replayed back to the lead day (model card caveat 7).

What one training row looks like

  • Key: ASIN, date, cost, store (the same kit Lead Score already takes: asin, date, cost, store URL).
  • Cost: for real leads, the lead cost. For could-have-bought rows, the store price on that date from catalog_history (the item's own sale price when it has one), × the event discount when a store-wide sale was on (0.75, or 0.65 for Sephora Collection; 1.0 otherwise), × 1.05 tax.
  • Inputs: v1's inputs, computed only from data dated on or before that day (Keepa histories are dated, so this is exact), plus new ones from the nearest snapshot on or before that day: each competitor's stock, total competitor stock, days of cover, and Buy Box seller.
  • Label: the same as v1, the average Buy Box price on days 18–78 after the date, from the latest keepa_raw. A row can be graded once 78 days have passed.
  • Sampling: one could-have-bought row per pair per week, plus a row on any day the store price or sale status changed. Rows of the same ASIN are near-copies, so tests split by ASIN and by date, never at random.

Size and when to upgrade

The database is on Render (order-ledger-db): 0.5 CPU, 1 GB RAM, 50 GB disk ($34 a month), upgraded Nov 11, 2026.

  • Disk: at today's size, 50 GB lasts about 4 years. At 30,000 ASINs it lasts about a year. When the disk passes 80% (40 GB), either add disk on Render (about $0.30 per GB a month) or move snapshot months older than 12 months to Parquet files in Dropbox and drop those partitions. The export already writes them as Parquet, so nothing is lost.
  • Keepa tokens: at 30,000 ASINs on the same schedule the collector would need about 200,000 tokens a day, more than the key's 180,000. Before adding a big store: pull cold ASINs every 7 days instead of 3, or move to a larger Keepa plan.
  • CPU / RAM: the Lead DB page and jobs use indexes, so 0.5 CPU / 1 GB is enough. Upgrade if pages start taking more than 2 seconds or the System map shows the database near its memory limit. Training never runs on the database.

Training locally or in the cloud

Either works the same way, because training reads files, not the live database:

  1. Run ENGINE_KEY=… python3 tools/export_training.py --out "~/Dropbox/Keepa data/lead_db" from the repo. The first run downloads everything (about 2 GB today, mostly Keepa products); each later run only downloads what changed since the last one.
  2. It writes catalog, candidates, feedback and runs as Parquet files (replaced each run), history/ and snapshots/ as add-only Parquet parts, and keepa_raw/ as chunk files of 80 Keepa products in the same format as past Lead Score pulls.
  3. Training code reads them with pandas or DuckDB (SELECT * FROM 'lead_db/snapshots/*.parquet').
  • Locally (your computer): needs Python with pandas and pyarrow, and about 3 GB of free disk now, growing about 9 GB a year. v1-size models train in minutes on a laptop.
  • In the cloud (a Claude session): the same script runs there; the session downloads in a few minutes and can save the model to the Lead Score server as before.
  • Neither slows the Hub: the export reads in pages of up to 5,000 rows, and the model is trained on the files.
